# โปรเจค_napat_67131315 — COURTBOOK

ระบบจองสนามแบดมินตันออนไลน์ตาม Wireframe Assessment 5 และเอกสาร CSI402 Requirements / Flowchart

**ผู้จัดทำ: ณภัทร พิชัยรัตน์ · รหัสนักศึกษา 67131315**

ASP.NET Core MVC (.NET 10) + SQLite บันทึกข้อมูลจริง แยกจากโปรเจกต์ Assessment 9–10 โดยใช้ฐานข้อมูลคนละไฟล์

รองรับ PostgreSQL ของ Supabase เพิ่มเติม ดู [วิธีตั้งค่า Supabase และย้ายข้อมูล SQLite](docs/SUPABASE.md) โดยค่าเริ่มต้นยังใช้ SQLite จนกว่าจะตั้งค่าการเชื่อมต่อ

เติมเครดิตอัตโนมัติแบบทดลองได้ที่ **กระเป๋าเงิน → เติมเครดิตอัตโนมัติแบบทดลอง** เลือกยอดแล้วกด **ชำระสำเร็จ** เครดิตจะเข้ากระเป๋าทันทีโดยไม่ใช้เงินจริงหรือรอผู้ดูแล มีตัวเลือกทดลองชำระไม่สำเร็จและยกเลิกด้วย รายการหมดอายุใน 15 นาทีและเติมซ้ำไม่ได้ ประวัติระบุ `DEMO-` ชัดเจน เครดิตทดลองใช้ยอดกระเป๋าเดียวกับระบบจองและแพ็กสมาชิก เปิด/ปิดได้ด้วย `Demo:AutomaticTopUps` (หรือ `Demo__AutomaticTopUps`) ระบบสร้างตาราง `DemoPayments` เพิ่มให้อัตโนมัติ โดยเก็บประวัติและยอดเดิมไว้ โหมดนี้ใช้ทดสอบขั้นตอนชำระเงิน ไม่ได้เชื่อมผู้ให้บริการรับเงินจริง

## เริ่มใช้งาน

ต้องมี .NET SDK 10 แล้วเปิด Terminal ในโฟลเดอร์นี้:

```powershell
dotnet restore
dotnet watch --project CourtBook.csproj
```

ดับเบิลคลิก `run.cmd` หรือรันคำสั่งข้างต้นเพียงครั้งเดียว แล้วเปิด:

- ลูกค้าบัญชีที่ 1: **http://localhost:5001** (`Customer.url`)
- ลูกค้าบัญชีที่ 2: **http://localhost:5003** (`Customer2.url`)
- ลูกค้าบัญชีที่ 3: **http://localhost:5004** (`Customer3.url`)
- ผู้ดูแลระบบ: **http://localhost:5002** (เปิดหน้าเข้าสู่ระบบผู้ดูแลอัตโนมัติ)

หลังเริ่มระบบ ใช้ไฟล์ทางลัดด้านบน หรือ `Admin.url` เพื่อเปิดฝั่งผู้ดูแลในเบราว์เซอร์ได้โดยตรง ไฟล์เหล่านี้เป็นทางลัดเปิดหน้าเว็บ ไม่ได้เริ่มเซิร์ฟเวอร์ใหม่

แต่ละพอร์ตเปิดเฉพาะหน้าของฝั่งนั้นและรับเฉพาะบัญชีตามบทบาท คุกกี้ลูกค้าแยกตามพอร์ต จึงล็อกอินลูกค้า 3 บัญชีพร้อมกันในคนละแท็บของเบราว์เซอร์เดียวได้ การออกจากระบบพอร์ตหนึ่งไม่ออกจากพอร์ตอื่น พอร์ตเดียวกันทุกแท็บจะใช้บัญชีเดียวกัน ทั้งหมดใช้ฐานข้อมูลร่วมกัน สนามและเวลาที่จองจึงตรงกันทุกบัญชี

หลังอัปเดตครั้งนี้ให้ล็อกอินลูกค้าใหม่ในแต่ละพอร์ต เพราะชื่อคุกกี้ถูกเปลี่ยนเพื่อแยกบัญชี หากต้องการช่องบัญชีเพิ่ม ให้เพิ่ม URL พอร์ตใหม่ใน `Urls` ของ `appsettings.json` โดยไม่ใช้พอร์ตผู้ดูแล 5002 ระบบจะแยกคุกกี้ของพอร์ตใหม่นั้นให้อัตโนมัติ

โปรแกรมจะสร้าง `App_Data/courtbook.db` อัตโนมัติ พร้อมสนาม A/B ราคา 200 บาทต่อชั่วโมง และโปรโมชั่น 5 แบบตาม Requirement

## วิธีทดลองครบเส้นทาง

1. เปิดหน้าแรก ดูสนามและโปรโมชั่นโดยยังไม่ต้องเข้าสู่ระบบ
2. สมัครสมาชิกใหม่ แล้วเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
3. เลือกสนามและวันพรุ่งนี้ เลือกเวลา 09:00, 10:00 และ 11:00
4. เลือกโปรโมชั่น **จองต่อเนื่อง** จะได้ 200 × 3 = 600 บาท ลด 15% = 90 บาท ยอดสุทธิ **510 บาท**
5. ส่งคำขอจอง จะได้รหัส `CB000001` พร้อมสถานะ “รอผู้ดูแลยืนยัน” และดูรายการได้ในประวัติของบัญชีตนเอง ช่วงเวลาถูกกันไว้ทันที
6. เข้าสู่ระบบด้วยสมาชิกอีกบัญชี เวลาที่จองแล้วจะเลือกไม่ได้ และดูผลการจองของผู้อื่นไม่ได้
7. เข้าสู่ระบบด้วยบัญชีผู้ดูแล เพื่อเพิ่ม/แก้สนาม ปิดบางช่วงเวลา ดูรายการจอง และเพิ่ม/แก้โปรโมชั่น
8. ปิดและเปิดโปรแกรมใหม่ ข้อมูลยังอยู่ ไม่ต้องลบไฟล์ฐานข้อมูลระหว่างเปลี่ยนรุ่นโค้ด

## กติกาธุรกิจ

- ให้บริการทุกวัน **08:00–22:00 น.** หน่วยจอง 1 ชั่วโมง เลือกชั่วโมงต่อเนื่องในสนามเดียวกันและวันเดียวกัน
- ใช้เวลาประเทศไทย UTC+7 และวันที่แบบปฏิทิน ไม่ใช้การหารจำนวนวินาทีเพื่อตัดสินสิทธิ์จองล่วงหน้า
- ห้ามจองย้อนหลัง สนามปิด ช่วงเวลาปิด หรือช่วงเวลาที่มีผู้จองแล้ว
- ช่วงเวลาที่เริ่มไปแล้วของวันปัจจุบันเลือกจองไม่ได้ โดยเทียบเวลาไทย UTC+7 หน้าที่เปิดค้างจะปิดช่วงเวลาที่หมดไปโดยอัตโนมัติและตรวจซ้ำเมื่อกลับมาเปิดหน้า ฝั่งเซิร์ฟเวอร์ตรวจใหม่ทุกครั้งก่อนบันทึก จึงไม่สามารถส่งคำขอข้ามข้อจำกัดนี้ได้
- ก่อนยืนยัน ระบบคำนวณราคาและตรวจสิทธิ์ใหม่จากฐานข้อมูล ไม่รับยอดเงินที่ส่งจากเบราว์เซอร์มาใช้
- ยอดก่อนส่วนลด = ราคาต่อชั่วโมง × จำนวนชั่วโมง; ยอดสุทธิ = ยอดก่อนส่วนลด − ส่วนลด โดยไม่ต่ำกว่า 0
- เก็บเงินเป็นจำนวนสตางค์เต็ม ใช้ decimal ในการคำนวณเปอร์เซ็นต์และปัดเศษครึ่งขึ้นที่สตางค์
- เลือกโปรโมชั่นได้ไม่เกินหนึ่งรายการต่อการจอง ช่วงใช้งานโปรโมชั่นอ้างอิง **วันที่ทำรายการ**
- ราคา ชื่อสนาม ชื่อโปรโมชั่น และยอดเงินในรายการเก็บเป็นค่าขณะยืนยัน การแก้ราคา/เปลี่ยนชื่อภายหลังไม่เปลี่ยนข้อมูลรายการเดิม
- รายการใหม่เป็น “รอผู้ดูแลยืนยัน” ผู้ดูแลยืนยันได้จากหน้ารายละเอียดการจอง หลังยืนยันแล้วจะแสดง “เสร็จสิ้น” เมื่อผ่านเวลาจอง
- หน้ายืนยันเป็นผลการจอง **ไม่ใช่หลักฐานการชำระเงิน** ตามเอกสาร Wireframe

### โปรโมชั่นเริ่มต้น 5 แบบ

| โปรโมชั่น | เงื่อนไข | ส่วนลด |
| --- | --- | --- |
| สมาชิกใหม่ | การจองครั้งแรกของบัญชี | 50 บาท |
| จองต่อเนื่อง | สนามเดียวกันต่อเนื่องอย่างน้อย 3 ชั่วโมง | 15% |
| ช่วงเช้าวันธรรมดา | จันทร์–ศุกร์ ทุกชั่วโมงอยู่ในช่วง 08:00–12:00 | 10% |
| จองล่วงหน้า | วันที่เล่นห่างจากวันที่ทำรายการอย่างน้อย 7 วันปฏิทิน | 80 บาท |
| ยอดจองครบ | ยอดก่อนส่วนลดตั้งแต่ 1,000 บาท | 100 บาท |

ผู้ดูแลเพิ่มโปรโมชั่นจากกติกา 5 ประเภทนี้ได้ แก้จำนวนส่วนลด ค่าขั้นต่ำ วันที่เริ่ม–สิ้นสุด และเปิด/ปิดได้

## ฐานข้อมูลและการป้องกันจองซ้ำ

ตารางหลัก: `Users`, `Courts`, `Promotions`, `Bookings`, `BookedSlots`, `BlockedSlots`

การยืนยันจองใช้ SQLite immediate transaction ตั้งแต่ตรวจเวลาว่าง ตรวจโปรโมชั่น สร้างรายการ ไปจนถึงจองทุกชั่วโมง ช่วงเวลามีคีย์หลัก `(CourtId, PlayDate, Hour)` ป้องกันการจองซ้ำระดับฐานข้อมูล ธุรกรรมเดียวกันยังป้องกันการใช้โปรโมชั่นครั้งแรกซ้ำจากคำขอพร้อมกัน

การแก้ตารางเวลาใช้ transaction เช่นเดียวกัน และไม่อนุญาตให้ผู้ดูแลปิดทับชั่วโมงที่มีการจองอยู่แล้ว

ใช้ PasswordHasher เก็บรหัสผ่านเป็นแฮช, คุกกี้ยืนยันตัวตน, Authorize แยกบทบาท, SQL parameters และ Anti-forgery token บนคำขอที่แก้ข้อมูล ประวัติและผลการจองกรองด้วยผู้ใช้จากคุกกี้ฝั่งเซิร์ฟเวอร์

## การทดสอบ

ตัวแอปใช้ .NET เท่านั้น Python 3 และ Node.js ใช้เฉพาะเครื่องมือทดสอบ

```powershell
dotnet build
python tests/smoke.py
```

ทดสอบซ้ำโดยจำลองเครื่องภาษาไทยที่ใช้ปฏิทิน พ.ศ. เพื่อป้องกันปีของวันที่จากฟอร์มคลาดเคลื่อน:

```powershell
dotnet build tests/CultureHost/CultureHost.csproj
$env:COURTBOOK_TEST_DLL = Join-Path $PWD 'tests/CultureHost/bin/Debug/net10.0/CultureHost.dll'
python tests/smoke.py
Remove-Item Env:COURTBOOK_TEST_DLL
```

สคริปต์ใช้ฐานข้อมูลชั่วคราวและพอร์ตว่าง ทดสอบสิทธิ์ บัญชี โปรโมชั่นครบ 5 แบบ สรุปยอด 510 บาท การปัดเศษ/จำกัดส่วนลด จองซ้ำแบบพร้อมกัน โปรโมชั่นครั้งแรกแบบพร้อมกัน ปิด–เปิดสนาม/เวลา การเก็บข้อมูลเดิม และข้อมูลหลังรีสตาร์ต

ทดสอบหน้าจอจริงด้วย Node.js 22+ และ Chrome ที่ตำแหน่งมาตรฐาน Windows:

```powershell
node tests/browser.mjs
```

ตรวจครบ 13 หน้าหลัก แบบฟอร์มผู้ดูแลเพิ่มเติม และความกว้างมือถือ 390px โดยบันทึกภาพที่ `docs/screenshots/` ผลล่าสุดอยู่ที่ `docs/screenshots/verification.json`

โหมด `Testing` ใช้กุญแจคุกกี้ในหน่วยความจำเพื่อให้รันในสภาพแวดล้อมจำกัดสิทธิ์ได้ ต้องระบุฐานข้อมูลชั่วคราวเป็นพาธเต็ม สคริปต์ตั้งค่าให้เอง การรันปกติใช้กุญแจคุกกี้มาตรฐานของ ASP.NET Core

## การจัดการโดยผู้ดูแล

เข้าสู่ระบบที่ http://localhost:5002 แล้วใช้เมนู:

- **รายการจอง**: เปิดรายละเอียดแล้วกดยืนยันการจอง ระบบบันทึกผู้ยืนยันและเวลา การจองที่รอยืนยันกันช่วงเวลาไว้แล้วเพื่อป้องกันจองซ้ำ
- **ยืนยันการชำระเงิน**: อยู่ในรายละเอียดรายการที่ยืนยันการจองแล้ว ตรวจรับยอดสุทธิครบก่อน กรอกเลขอ้างอิงหรือรายละเอียดการรับเงินสดแล้วกดยืนยัน ระบบบันทึกผู้รับเงินและเวลา และป้องกันการเขียนทับการรับเงินเดิม
- **บัญชีลูกค้า**: ดูชื่อ อีเมล และประวัติการจองรายคน
- **ประเภทกีฬา**: เพิ่มประเภท เช่น ฟุตบอล เทนนิส แล้วเลือกประเภทในหน้าเพิ่ม/แก้ไขสนาม ลูกค้าเห็นประเภทในรายการสนามและตารางเวลา
- **ตารางเวลา**: ทำเครื่องหมายช่วงที่ไม่ว่าง/ปิดรับจอง เอาเครื่องหมายออกเพื่อเปิดช่วงเวลา ช่วงที่มีรายการจองอยู่จะแก้ไขทับไม่ได้ ปิดทั้งสนามได้ในหน้าแก้ไขสนาม
- **รูปสนาม**: ไปที่จัดการสนาม → เพิ่มสนามหรือแก้ไข → เลือกรูปสนาม ดูภาพตัวอย่างแล้วบันทึก รองรับ JPG, PNG และ WebP ขนาดไม่เกิน 5 MB แนะนำรูปแนวนอน 1600 × 1000 พิกเซล รูปจะแสดงในหน้าแรก ตารางสนาม และหน้าจอง รวมถึงรายการสนามของผู้ดูแล เปลี่ยนรูปได้ด้วยการเลือกไฟล์ใหม่ หรือติ๊ก “ลบรูปเดิม” แล้วบันทึก การแก้ไขข้อมูลโดยไม่เลือกไฟล์จะเก็บรูปเดิม รูปถูกเก็บในฐานข้อมูลเดียวกับสนาม จึงคงอยู่หลังรีสตาร์ตและรวมอยู่ในการสำรองฐานข้อมูล สนามที่ยังไม่มีรูปใช้ภาพกราฟิกแทน

ลูกค้าดูสถานะการยืนยันและการรับเงินล่าสุดได้ในประวัติหรือรายละเอียดรายการเมื่อรีเฟรช

### ชำระเงินด้วย QR พร้อมเพย์

หลังลูกค้าส่งคำขอจอง ระบบแสดง QR และยอดสุทธิหลังหักโปรโมชั่นทันทีที่ด้านบนของหน้ารายละเอียด หรือกลับมาเปิดด้วยปุ่ม “ชำระเงินผ่าน QR” ในประวัติการจองได้ โดยไม่ต้องรอผู้ดูแลอนุมัติก่อน สแกนหรือบันทึกรูป QR แล้วเลือกจากอัลบั้มในแอปธนาคาร QR นี้ไม่ระบุยอด ลูกค้าต้องกรอกยอดตามรายการและตรวจชื่อผู้รับก่อนโอน จากนั้นแนบสลิป JPG/PNG/WebP ไม่เกิน 5 MB พร้อมเลขรายการโอน ระบบแสดง “รอตรวจสอบการชำระเงิน” ผู้ดูแลดูสลิปในรายละเอียดรายการ ยืนยันการจอง และตรวจเงินที่เข้าจริงก่อนยืนยันรับเงิน

สลิปถูกเก็บในฐานข้อมูลและให้ดูเฉพาะเจ้าของรายการหรือผู้ดูแล การส่งสลิปไม่ยืนยันรับเงินอัตโนมัติ และไม่สามารถแก้หลักฐานหลังผู้ดูแลยืนยันรับเงินแล้ว หากแจ้งโอนแล้วต้องติดต่อผู้ดูแลเรื่องยกเลิกเพื่อจัดการเงินที่อาจโอนไปแล้ว รายการยอดสุทธิ 0 บาทไม่แสดง QR และไม่ต้องโอนเงิน

รูป QR ต้นฉบับอยู่ที่ `wwwroot/images/payment-qr.jpg` ใช้ไฟล์ที่ได้รับโดยไม่แก้ไขหรือสร้าง QR ใหม่ ระบบไม่ได้เชื่อม API ธนาคารเพื่อยืนยันธุรกรรมอัตโนมัติ

ลูกค้ายกเลิกได้จาก **ประวัติการจอง → รายละเอียด → ยกเลิกการจอง → ยืนยันยกเลิกการจอง** เฉพาะรายการของตนเองที่ยังไม่ถึงเวลาเริ่มและยังไม่ได้ยืนยันชำระเงิน ใช้ได้ทั้งรายการรออนุมัติและยืนยันแล้ว ระบบคืนช่วงเวลาในธุรกรรมเดียวและเก็บประวัติพร้อมเวลายกเลิกไว้ให้ทั้งสองฝั่งดู รายการที่ชำระเงินแล้วให้ติดต่อผู้ดูแลเพื่อจัดการยกเลิกและคืนเงิน สิทธิ์โปรโมชั่นจองครั้งแรกจะกลับมาเมื่อไม่มีรายการที่ยังไม่ถูกยกเลิก

## อัปเกรดฐานข้อมูลเดิม

หยุดโปรแกรมเดิมก่อนอัปเกรดและสำรอง `App_Data/courtbook.db` ขณะโปรแกรมหยุด การเริ่มระบบเวอร์ชันใหม่จะเพิ่มตารางประเภทกีฬาและคอลัมน์การยืนยันในธุรกรรมเดียว สามารถรันซ้ำได้ บัญชี รายการจอง ราคา และช่วงเวลาที่จองเดิมจะคงอยู่ สนามเดิมกำหนดประเภทเริ่มต้นเป็นแบดมินตัน รายการเดิมคงสถานะยืนยันตามเดิมและไม่ถูกระบุว่าชำระเงินจนกว่าผู้ดูแลจะยืนยันรับเงิน

หากต้องย้อนเวอร์ชัน ให้หยุดโปรแกรมและคืนทั้งโปรแกรมกับฐานข้อมูลสำรองที่ตรงกัน อย่ารันโปรแกรมเก่าและใหม่พร้อมกันบนฐานข้อมูลเดียวกัน

## กระเป๋าเงินและแพ็กสมาชิก

- ลูกค้าเข้าเมนู **กระเป๋าเงิน** (`/Wallet`) เพื่อดูยอดคงเหลือ ประวัติ เติมเงิน และซื้อแพ็ก
- เติมเงินครั้งละ 1–100,000 บาท: โอนผ่าน QR เดิม แนบสลิปและเลขรายการโอน แล้วรอผู้ดูแลตรวจสอบ เงินจะยังไม่เข้าจนกว่าจะอนุมัติ
- ผู้ดูแลเข้า **คำขอเติมเงิน** (`/Admin/TopUps`) เปิดสลิปและตรวจรายการรับเงินจริงในธนาคารก่อนอนุมัติ หรือระบุเหตุผลไม่อนุมัติ ระบบไม่ได้เชื่อมธนาคารเพื่อยืนยันยอดอัตโนมัติ
- ป้องกันการใช้เลขโอนและรูปสลิปเดิมซ้ำระหว่างเติมเงินกับค่าจอง แต่รูปสลิปที่แก้ไขแล้วอาจมีข้อมูลไฟล์ต่างกัน ผู้ดูแลต้องตรวจเงินจริงทุกครั้ง
- ตั้งราคาและเปอร์เซ็นต์ส่วนลดได้ที่ **แพ็กสมาชิก** (`/Admin/Plans`) มีรายเดือน 1 เดือน และรายปี 12 เดือน เริ่มต้นปิดขายทั้งคู่จนผู้ดูแลตั้งค่าและเปิดขาย
- แพ็กเริ่มวันที่ซื้อ ใช้ได้ถึงวันก่อนวันครบกำหนดตามปฏิทิน ไม่มีการต่ออายุอัตโนมัติ และซื้อใหม่ได้เมื่อแพ็กเดิมหมดอายุ
- สิทธิ์แพ็กเป็นส่วนลดค่าจองสำหรับวันที่เล่นในช่วงอายุแพ็ก เลือกส่วนลดที่มากกว่าระหว่างแพ็กกับโปรโมชั่นที่ลูกค้าเลือก โดยไม่รวมซ้อนกัน การแก้ราคา/สิทธิ์หรือปิดขายไม่เปลี่ยนสิทธิ์ที่ซื้อแล้ว
- ชำระค่าจองจากกระเป๋าได้ที่หน้ารายละเอียดการจอง เฉพาะรายการที่ยังไม่ชำระและยังไม่แจ้งโอน การจ่ายไม่เปลี่ยนขั้นตอนยืนยันการจองของผู้ดูแล
- การเพิ่มยอด การซื้อแพ็ก และการชำระค่าจองใช้ธุรกรรมฐานข้อมูล ป้องกันเครดิตหรือหักเงินซ้ำจากคำขอพร้อมกันและไม่อนุญาตยอดติดลบ
- รายการที่ชำระแล้วต้องติดต่อผู้ดูแลกรณียกเลิก/คืนเงิน เช่นเดียวกับการชำระผ่าน QR เดิม

ตารางใหม่ `TopUps`, `WalletEntries`, `MembershipPlans`, `Memberships` สร้างเมื่อเปิดแอป โดยเก็บประวัติเงินเป็นจำนวนสตางค์และคงข้อมูลผู้ใช้/การจองเดิม

ตรวจเส้นทางเติมเงิน อนุมัติซ้ำ ซื้อแพ็ก ส่วนลด วันหมดอายุ ชำระค่าจองพร้อมกัน และข้อมูลหลังรีสตาร์ต ด้วยฐานข้อมูลชั่วคราว:

```powershell
dotnet build
python tests/wallet_smoke.py
```

### เช่าอุปกรณ์เสริม

หน้าเลือกวันและเวลาเลือกเช่าไม้แบดมินตัน (50 บาท/อัน) และรองเท้ากีฬา (30 บาท/คู่) ได้ 0–10 ต่อรายการ คิดค่าเช่าต่อการจองหนึ่งครั้ง ใช้ในช่วงเวลาเดียวกับสนาม ราคานี้เป็นรายการเริ่มต้นสำหรับกีฬาแบดมินตัน ผู้ดูแลเพิ่มและแก้ไขชื่อ ราคา หน่วยนับ ประเภทกีฬา และเปิด–ปิดให้เช่าได้ที่เมนู **อุปกรณ์เสริม** (`/Admin/Equipment`) แต่ละรายการผูกกับกีฬาเดียว หน้าจองและเซิร์ฟเวอร์รับเฉพาะอุปกรณ์ที่เปิดให้เช่าของกีฬาที่เลือก กีฬาที่ยังไม่มีอุปกรณ์ยังจองสนามได้ตามปกติ ระบบยังไม่ได้ตรวจสต็อกอุปกรณ์แยกตามช่วงเวลา

ส่วนลดโปรโมชั่นและแพ็กสมาชิกคำนวณจากค่าจองสนาม ค่าอุปกรณ์บวกเพิ่มเต็มจำนวน รวมชำระผ่าน QR หรือกระเป๋าเงิน รายการ ชื่อ ราคา และจำนวนถูกบันทึกไว้ใน `Bookings.EquipmentJson` เพื่อคงประวัติเดิมแม้แก้ไขรายการภายหลัง ฐานข้อมูล SQLite และ Supabase เพิ่มคอลัมน์นี้อัตโนมัติเมื่อเริ่มระบบ

## COURTBOOK รุ่นแค็ตตาล็อกและสมาชิก

- หน้าแรกภาษาไทย ธีมดำ/เทา/เขียวนีออน พร้อมกีฬาแบดมินตัน ฟุตบอล เทนนิส รูปประกอบ ตัวกรองกีฬา โปรโมชั่น และแพ็กรายเดือน/รายปี
- ค้นหาสนามด้วยกีฬา สถานที่ วันที่ และสนาม; ดูรายละเอียดราคาและรีวิวจริง; เลือกเวลาเริ่ม–สิ้นสุดหรือเลือกชั่วโมงต่อเนื่อง
- ผู้ดูแลระบุสถานที่จริงในหน้าจัดการสนาม หากยังไม่ระบุจะแสดง “ยังไม่ระบุสถานที่”; ไม่มีการสร้างคะแนนรีวิวจำลอง
- รีวิวได้หลังเล่นจบจากรายการจองที่ยืนยันแล้ว หนึ่งคะแนนต่อบัญชีต่อสนามและแก้ไขได้
- อุปกรณ์ผูกประเภทกีฬา รูปภาพกำหนดได้ในหน้าผู้ดูแล ค่าเริ่มต้นเป็นตัวอย่างที่แก้ไข/ปิดให้เช่าได้ เช่น ไม้แบดมินตัน ชุดลูกแบดมินตัน ลูกฟุตบอล เสื้อแบ่งทีม ไม้เทนนิส ชุดลูกเทนนิส
- แพ็กรายเดือน (1 เดือน) และรายปี (12 เดือน) ผู้ดูแลตั้งราคาและส่วนลดที่ `/Admin/Plans` ก่อนเปิดขาย; แพ็กระดับเดิมปิดการขาย โดยสิทธิ์ที่ซื้อไปแล้วคงอยู่จนครบอายุ
- โปรโมชั่นกลุ่มกำหนดผู้เล่นขั้นต่ำที่หน้าผู้ดูแล ลูกค้าระบุจำนวนผู้เล่นในหน้าจอง ส่วนลดคิดเฉพาะค่าจองสนาม
- `/Admin/Revenue` รายงานตามวันใช้สนาม แยกยอดรับเงินจริง ยอดรอชำระ และการยกเลิก ไม่รวมเงินเติมกระเป๋า/การขายแพ็กซ้ำเป็นค่าจอง
- สมาชิกแก้ไขชื่อ/อีเมลได้ เปลี่ยนอีเมลต้องยืนยันรหัสผ่านปัจจุบัน; ผู้ดูแลระงับ/เปิดบัญชีได้จากรายละเอียดลูกค้า ประวัติและเงินคงเดิม

### ตั้งค่าการกู้รหัสผ่าน

ตั้งค่าใน User Secrets หรือ environment เท่านั้น ห้ามเก็บรหัสผ่าน SMTP ใน repository:

```powershell
dotnet user-secrets set "Email:Host" "YOUR_SMTP_HOST"
dotnet user-secrets set "Email:From" "YOUR_SENDER_EMAIL"
dotnet user-secrets set "Email:Username" "YOUR_SMTP_USERNAME"
dotnet user-secrets set "Email:Password" "YOUR_SMTP_PASSWORD"
dotnet user-secrets set "Email:Port" "587"
dotnet user-secrets set "Account:PublicOrigin" "https://YOUR_CUSTOMER_HOST"
dotnet user-secrets set "Account:AdminOrigin" "https://YOUR_ADMIN_HOST"
```

ใช้ Development เพื่อโหลด User Secrets; บนเซิร์ฟเวอร์ใช้ `Email__Host` และชื่อคีย์แบบเดียวกัน SMTP เปิด TLS โดยค่าเริ่มต้น หากไม่ตั้งค่าจะระบุว่าระบบอีเมลไม่พร้อม ไม่แสดงหรือคืน reset token ให้ผู้ร้องขอ ลิงก์หมดอายุ 30 นาที ใช้ได้ครั้งเดียวและผูกกับบัญชี/ประเภทพอร์ทัล เปลี่ยนรหัสผ่านแล้วเซสชันเดิมใช้ไม่ได้ คำขอส่งอีเมลและรีเซ็ตจำกัด 5 ครั้งต่อ IP ต่อ 15 นาทีต่อ endpoint

สำหรับทดสอบภายใน Development/Testing เท่านั้น ตั้ง `Email__Delivery=Pickup` และ `Email__PickupDirectory` เป็นโฟลเดอร์ส่วนตัวเพื่อเก็บไฟล์ `.eml`; ห้ามเปิด Pickup บน production และห้ามนำโฟลเดอร์นี้ไว้ใน wwwroot

### ภาพประกอบและการตรวจสอบ

## แจ้งสนามและอุปกรณ์ชำรุด

ลูกค้าเปิด **การจองของฉัน → รายละเอียดการจอง → แจ้งสนาม / อุปกรณ์ชำรุด** เลือกแจ้งสนาม หรืออุปกรณ์ที่เช่าในรายการนั้น และระบุรายละเอียด 5–2,000 ตัวอักษร รายการที่ยกเลิกแล้วส่งรายงานใหม่ไม่ได้ ลูกค้าอ่านรายงานและคำตอบได้เฉพาะการจองของตนเอง

ผู้ดูแลใช้เมนู **แจ้งชำรุด** (`/Admin/DamageReports`) กรองรายงาน และเปลี่ยนสถานะ **รอตรวจสอบ → กำลังดำเนินการ → แก้ไขแล้ว** พร้อมหมายเหตุถึงลูกค้าได้ ระบบบันทึกผู้แก้ไขและเวลาล่าสุด ไม่มีการปิดสนามหรือปิดอุปกรณ์อัตโนมัติ ผู้ดูแลจัดการต่อที่ตารางเวลาหรืออุปกรณ์เสริมตามผลตรวจสอบ

ข้อมูลเก็บใน `DamageReports` เชื่อมรายการจอง พร้อมชื่ออุปกรณ์จาก snapshot เดิม รองรับ SQLite และ schema Supabase ที่เปิด RLS การส่งรายงานและอัปเดตสถานะต้องผ่าน CSRF และตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ ชุด `tests/product_smoke.py` ตรวจเจ้าของรายการ การปลอมอุปกรณ์/สถานะ การติดตามคำตอบ การกรองสถานะ และการเก็บข้อมูลหลังรีสตาร์ต

### แจ้งปัญหาได้โดยไม่ต้องมีรายการจอง

เปิดเมนู **แจ้งปัญหา** หรือ `/Bookings/ReportDamage` เลือก **ปัญหาทั่วไป / สนาม / อุปกรณ์** ระบุหัวข้อได้ตามต้องการ แล้วพิมพ์รายละเอียดส่งผู้ดูแล หน้าข้อผิดพลาดมีแบบฟอร์มเดียวกันสำหรับสมาชิกที่เข้าสู่ระบบ ลูกค้ามองเห็นเฉพาะข้อความและคำตอบของตนเอง ส่วนผู้ดูแลอ่านและตอบกลับที่เมนู **ข้อความแจ้งปัญหา**

`DamageReports` รุ่นใหม่เก็บ UserId ของผู้ส่งโดยตรงและให้ BookingId ว่างได้ การอัปเกรด SQLite ย้ายรายงานเดิมและข้อมูลคำตอบทุกช่องภายใน transaction เดียว ส่วน PostgreSQL เพิ่มคอลัมน์และ backfill จากเจ้าของรายการจองก่อนยกเลิกข้อบังคับ BookingId หยุดเซิร์ฟเวอร์เดิมก่อนเปิดรุ่นใหม่ ไม่รันสองเวอร์ชันกับฐานเดียวกันพร้อมกัน สำรองฐาน SQLite ก่อนอัปเกรด; หากต้องย้อนเวอร์ชันให้ใช้ทั้งโปรแกรมและฐานสำรองเดิม ไม่ลบรายงานใหม่เพื่อย้อน schema

## ใบเสร็จและหลักฐานการเข้าสนาม

ระบบออกใบเสร็จอัตโนมัติเมื่อผู้ดูแลยืนยันรับชำระค่าจอง เมื่อหักกระเป๋าเงินชำระค่าจองสำเร็จ และเมื่อซื้อแพ็กรายเดือน/รายปีสำเร็จ การแนบสลิปที่ยังไม่ได้รับการตรวจไม่ออกใบเสร็จ ลูกค้าเปิดได้จากรายละเอียด/ประวัติการจอง กระเป๋าเงิน หรือ **ใบเสร็จของฉัน** (`/Receipts`) การซื้อแพ็กที่สำเร็จพาไปหน้าใบเสร็จทันที

ปุ่ม **พิมพ์ / บันทึก PDF** ใช้หน้าต่างพิมพ์ของเบราว์เซอร์ เลือก Save as PDF เพื่อเก็บไฟล์ รูปแบบพิมพ์ใช้พื้นขาว ตัวอักษรดำ และซ่อนเมนู ใบเสร็จมีเลข `RC-BK-...` สำหรับค่าจอง และ `RC-MB-...` สำหรับแพ็ก พร้อมชื่อผู้ชำระ รายการ ราคาที่บันทึก ส่วนลด ยอดรับชำระ และเวลา

ใช้ใบเสร็จค่าจองพร้อมรหัส CB ให้เจ้าหน้าที่ตรวจสอบสถานะปัจจุบันก่อนเข้าสนาม ต้องชำระและยืนยันการจองแล้ว และใช้เฉพาะวันเวลาที่จอง ใบเสร็จของรายการที่ยังรอยืนยัน/ยกเลิก/พ้นเวลาแสดงสถานะตามจริง ใบเสร็จแพ็กบอกสิทธิ์ส่วนลดและอายุแพ็ก ลูกค้ายังต้องจองสนามตามปกติ

`PaymentReceipts` เก็บ snapshot ชื่อ/อีเมล รายการ และยอด ณ ตอนชำระ การแก้โปรไฟล์ สนาม หรือราคาแพ็กภายหลังไม่แก้ใบเสร็จเดิม การออกใบเสร็จอยู่ใน transaction เดียวกับการรับเงิน/หักยอด และใช้เลขอ้างอิงเดิมเมื่อเรียกซ้ำ รายการชำระเดิมที่ยังไม่มีใบเสร็จจะสร้างให้อัตโนมัติเมื่อเริ่มแอป ข้อมูลชื่อสำหรับรายการเก่าอ้างอิงข้อมูลที่มีขณะสร้างย้อนหลัง ไม่สามารถย้อนชื่อที่ไม่ได้เก็บในระบบเดิมได้

ลูกค้าเข้าถึงใบเสร็จเฉพาะของตนเอง ผู้ดูแลตรวจได้จากรายละเอียดการจองหรือ `/Admin/Receipt/{เลขใบเสร็จ}`; ตาราง Supabase เปิด RLS โดยไม่มี anonymous policy ชุดทดสอบตรวจการออกเฉพาะรายการสำเร็จ การป้องกันข้ามบัญชี การออกซ้ำ ความคงเดิมของ snapshot การย้อน transaction เมื่อเขียนใบเสร็จไม่สำเร็จ การพิมพ์ PDF และข้อมูลหลังรีสตาร์ต

### แยกหน้ากระเป๋าเงินกับแพ็กสมาชิก

## บัญชีและการคืนเงิน

- ลูกค้า: เมนู **บัญชีและการชำระเงิน** ในกระเป๋าเงินหรือหน้าบัญชี (`/Accounting`) แสดงยอดค่าจอง ซื้อแพ็ก เติมเงิน คืนเงิน และ CSV เฉพาะของตนเอง
- ผู้ดูแล: **บัญชีรายรับ–รายจ่าย** (`/Admin/Accounting`), **บันทึกรายจ่าย** (`/Admin/Expenses`), **คำขอคืนเงิน** (`/Admin/Refunds`)
- รายงานเลือกช่วงวันได้สูงสุด 366 วัน รวมวันต้นและวันปลาย ตามเวลาไทย ยอดกระเป๋าเป็นยอดปัจจุบันทั้งหมด
- เงินรับภายนอกนับยอดเติมเงินธนาคารที่อนุมัติและค่าจองที่ชำระโดยตรง การใช้กระเป๋าและซื้อแพ็กไม่ถูกนับซ้ำ เครดิตทดลองแสดงแยก รายการรายจ่ายยกเลิกไม่รวมยอด
- ลูกค้าส่งคำขอคืนเต็มยอดค่าจองรวมอุปกรณ์ได้ 1 ครั้งต่อรายการ ก่อนเริ่มใช้งาน เมื่อชำระแล้วและยังไม่ยกเลิก ผู้ดูแลอนุมัติหรือปฏิเสธพร้อมหมายเหตุได้ การอนุมัติคืนเป็นเครดิตกระเป๋า COURTBOOK ยกเลิกการจองและปล่อยช่วงเวลาในธุรกรรมเดียว ระบบนี้ไม่โอนเงินออกธนาคารและไม่คืนแพ็กสมาชิก
- ใบเสร็จเดิมเก็บยอดชำระเดิม พร้อมแสดงสถานะคืนเงินและสถานะการเข้าสนามล่าสุด
- รายจ่ายเก็บวันที่ หมวด ผู้รับเงิน ช่องทาง เลขอ้างอิง ผู้บันทึกและเวลา หากบันทึกผิดให้ยกเลิกพร้อมเหตุผล ระบบเก็บประวัติและผู้ยกเลิกไว้
- เป็นรายงานดำเนินงานจากรายการในระบบ ไม่ได้สร้างงบการเงิน ภาษี หรือใบกำกับภาษี
- ฐานข้อมูล SQLite เพิ่มตาราง `Expenses` และ `BookingRefunds` อัตโนมัติ ส่วน Supabase รวมตารางและ RLS ใน `Database/supabase.sql` พร้อมรองรับการส่งออกข้อมูลเดิม
- ตรวจสอบ: `python tests/accounting_smoke.py` หลัง Build (กำหนด `COURTBOOK_TEST_DLL` หากใช้ผล Build ในโฟลเดอร์อื่น)


## แพ็กรวมชั่วโมงสนาม

- ที่ผู้ดูแล > แพ็กสมาชิก ตั้ง `MonthlyHours` (0–100 ชั่วโมงต่อรอบเดือน), ประเภทกีฬา, ราคา และส่วนลดชั่วโมงเกินโควตาได้ ค่า 0 คงแพ็กส่วนลดแบบเดิม โควตาใหม่ต้องตั้งจำนวนชั่วโมงและกีฬาก่อนเปิดขาย ไม่มีการเพิ่มชั่วโมงให้การซื้อเดิมอัตโนมัติ
- ทุกสนามในประเภทกีฬาที่เลือกใช้สิทธิ์ได้ ส่วนลดชั่วโมงเกินโควตาใช้กับกีฬานั้นด้วย ค่าอุปกรณ์ชำระแยก
- รอบเดือนอิงวันเริ่มแพ็กและวันที่เล่น เช่น เริ่ม 31 มกราคม รอบถัดไปเริ่ม 28/29 กุมภาพันธ์ แล้ว 31 มีนาคม ไม่ทบยอด รายปีได้โควตาแต่ละรอบเดือนจนครบ 12 เดือน ลูกค้าเห็นยอดของแต่ละรอบที่หน้าแพ็กสมาชิก
- กันโควตาทันทีที่ส่งคำขอจอง ภายในธุรกรรมเดียวกับการจองสนาม รองรับการจองพร้อมกัน หากโควตาที่แสดงในฟอร์มเปลี่ยน จะให้ตรวจยอดใหม่ก่อนยืนยัน
- ยกเลิกการจองแล้วโควตารอบเดิมกลับมา หากรอบหมดอายุไม่สามารถย้ายไปใช้รอบใหม่ กรณีมีเงินชำระให้ใช้คำขอคืนเงิน ผู้ดูแลอนุมัติแล้วคืนทั้งเงินเข้ากระเป๋าและโควตาของรายการนั้น
- รายการที่โควตาครบยอด 0 บาทออกหลักฐานใช้สิทธิ์ทันที และยังต้องรอผู้ดูแลยืนยันการจองก่อนเข้าสนาม ยกเลิกก่อนเริ่มเล่นได้โดยไม่ต้องขอคืนเงิน
- เทียบสิทธิ์แพ็กกับโปรโมชั่นที่เลือก ใช้แบบที่ลดได้มากกว่า หากเท่ากันใช้โปรโมชั่นเพื่อรักษาโควตา ไม่รวมซ้อนกัน
- เก็บจำนวนชั่วโมง กีฬา ส่วนลด และราคา ณ วันที่ซื้อ พร้อมรายละเอียดในเอกสาร การแก้แพ็กไม่เปลี่ยนสิทธิ์หรือใบเสร็จของผู้ซื้อเดิม
- SQLite เพิ่มคอลัมน์และตาราง `MembershipQuotaUses` อัตโนมัติ Supabase มีโครงสร้างใน `Database/supabase.sql` และรองรับในตัวส่งออกข้อมูล ตรวจสอบด้วย `python tests/quota_smoke.py`
